- Time and word-count tests draw from a chosen common-word list — top 200 (default, Monkeytype's default "english" list), 1k, 5k or 10k — set in settings or the palette (`src/words.js`; current corpus version v5). The word list is part of the test conditions, so bests and retests never mix lists. Original quote tests; quote length and descriptive difficulty filters; explicit empty-filter recovery.
- Saved theme, text size, word highlight (off, this word or next word; display only, never in the conditions; `wordHighlight` in `src/profile.js`), one-line tape, speed unit, word list, keyboard layout, keyboard, finger map, live metrics, stop-on-error, focus and sound preferences. The speed unit (wpm by default, or cpm = wpm × 5) is display only: scores, bests, comparisons, condition keys and stored settings stay in wpm (`src/units.js`). Speeds a person sets (the minimum speed options and the custom pace) are shown and entered in the chosen unit and saved in wpm. Focus mode has an exit and Escape support. The one-line tape (off by default) shows the practice passage on a single line that steps a word-aligned chunk at a time near the right edge (`src/tape.js`), never letter by letter; it is a display preference, not a test condition, like text size, and races keep three lines: a ghost race (so the friend's caret stays in view however far ahead or behind), one-keyboard and online races. `body[data-tape]` is the layout on screen, false during a ghost race, and the passage code reads it rather than the preference. Code passages use it too: a snippet is already typed as one run of space-separated tokens (`src/code-snippets.js`).
- Typing sounds (`src/sound.js`), off by default: clicks, or clicks plus a low tick for a mistyped letter, with a 0–100 volume (0 is silent). Synthesised with Web Audio (no files). The context lives in one of three states (`want` in `createSounds`): closed, asleep (built, suspended) or awake (running), and `reconcile` moves it there. Choosing an audible sound or volume builds it just after the change, while the page still has the gesture's activation, and leaves it asleep, so nothing runs before a run starts; the first key resumes it and clicks (and starts a context the browser built suspended, as WebKit does). When sound arrives any other way (a reload, an import, a sign-in), nothing is built until the first audible key, which asks for the context and is itself silent. It is never built inside an event handler, and never at page load. It is suspended while the tab is hidden and 250 ms after any run ends (practice, either race, composing; `runChanged` in `src/app.js`), including a context whose deferred build lands after the run, and resumed by the next key, even one that arrives while a suspend is still in flight. So a context runs only during a run or within 250 ms of a key. Any preference change that leaves sound off or at volume 0 closes it (`applySoundPreferences`), and so does a key that finds it so. Each key sounds its scored outcome under the run's correction rules: a wrong letter ticks, including the key that fails a fail-on-error run, and so does a space strict space refuses, since it scores as a wrong key; a key stop on error holds back, or one ignored while a quick-end-off run waits for space, clicks, and so does the space that submits that run; a backspace no backspace refuses is silent. Practice, code mode, lessons, drills and both races share that path. An accent (dead-key) commit sounds once, when it is scored, never for the accent key too, and ticks if any character in it scored as a mistake ("h onto ah ticks for the mark, whether the h is scored or held back). `keyOutcome` in `src/sound.js` makes that one decision per key from scoring's own changes, for practice and the online race alike. Watch replay and ghost carets never play. Composing practice clicks on counted input and never ticks. Reduced motion does not mute it. Presentational only: scoring never reads it.
- Import from Monkeytype (15 October 2026, `src/monkeytype.js`): the last row of settings, or "import Monkeytype settings…" in the palette, opens a dialog that takes the JSON Monkeytype's settings page exports (danger zone → import/export settings → export), pasted or from a file. Settings with a counterpart are applied as picks (`saveChoice`), so they sync and outrank older values from other devices: mode, time and words (a preset, or a custom length within `src/lengths.js` bounds: 5–600 s, 5–500 words), punctuation, numbers, language (english top 200/1k/5k/10k), quote length, correction, strict space, quick end, minimum accuracy and speed, repeat quotes (`typing` → on), pace caret and custom speed, live speed/accuracy, speed unit (`typingSpeedUnit` wpm or cpm; Monkeytype's wps, cps and wph are skipped, and its speeds are wpm whatever the unit, so they import unconverted), keymap, keymap layout (qwerty, dvorak, colemak, colemak_dh, workman → keyboard layout), font size (rem to small/medium/large), tape mode (word or letter → one-line tape on; Stilltype's tape steps by whole words either way, and the report says so), typing sounds (`playSoundOnClick` on → clicks, with `playSoundOnError` on → clicks + error tick; on is a numbered sound or, in older exports, `true`, and off is `off` or `false`; any other value is skipped, and so is an error sound without clicks, since the tick only plays with clicks), sound volume (`soundVolume` 0–1 → the nearest 5%) and theme (auto switch → system, otherwise light or dark by the theme's background). Correction takes the strongest rule asked for, in this order: `difficulty` master → fail on any error, expert → fail on word error; then `stopOnError` letter or word → stop on error (word is approximated, since Stilltype stops at the letter, and the report says so); then `confidenceMode` max → no backspace; free when all are off. Rules that lose are reported as skipped, and confidence mode `on` (backspace allowed within a word) has no counterpart. A custom minimum (`minAccCustom`, `minWpmCustomSpeed`) rounds down to the nearest offered value, so it never stops a run Monkeytype would have let continue; below the lowest (80%, 20 wpm) it is skipped. Monkeytype's `layout` remaps typed keys, which Stilltype never does, so a non-default one is reported as skipped. The report lists what was brought over and the counterparts left as they were, with why (zen mode, an endless or out-of-range length, a non-English language); Monkeytype-only keys are ignored. No migration: it writes the existing `preferences` column.
- Keyboard layouts (8 October 2026): QWERTY (default), Dvorak, Colemak, Colemak-DH (ANSI, angle mod) and Workman, in settings and the palette (`src/layouts.js`). The layout relabels the on-screen keyboard and its optional finger map (a mono finger initial on each key, a faint band behind alternate fingers, hands split, a legend; hidden with the keyboard below 760px). There is no emulation: people remap in the OS, so typed characters are scored as they arrive. The layout is part of the test conditions, so bests, retests, ghost pace, recurring evidence and the daily best never mix layouts; the conditions line names it only when it isn't QWERTY. `conditionKey` for QWERTY, and for every run saved before layouts, is byte-identical to before (tested), so old bests still match. Drills and pair evidence are character-based and need no change.
- Strict space and quick end (settings and palette). Strict space, off by default, refuses a space typed where the passage has a letter: it counts as a wrong key at that position (an `accepted: false` insert, which replay v1 already scored), the caret stays and the skipped letter is tinted until the next key. Quick end, on by default, is master's rule for continue on error: a word or quote run ends on its last letter, right or wrong. Off, a mistake in the last word holds the run until it is fixed or space submits it (a `submit` event replay ignores). Stop on error keeps master's rule too, waiting for every letter: quick end doesn't apply there, because on by default it would change existing stop-on-error runs and their bests. Which rules a session can take is read from that session (its kind, timing and run conditions; `ruleLimits` in `src/app.js`), never from the test-shape preferences: wherever quick end can't change the run (timed runs, every drill whatever its baseline, stop on error) its switch is disabled, keeps its value and says why, and the run records it at the default. A rule change restarts the session as the same kind (a drill stays a drill); the daily and a retest keep the rules they started with (a retest takes its baseline's, so it stays comparable) and say so, as does a one-keyboard race under way (both players race under the rules it started with; on that tab the switches otherwise act on the next race, an untimed quote whatever the practice shape), and the preference waits for the next run: starting a retest or drill never copies the baseline's rules into the preferences, and the footer best follows the retest's own conditions. Other screens stay put; a practice passage left waiting there is rebuilt when practice is shown. Each rule is in `conditionKey` only when it differs from the default and applies, so existing bests keep their keys.
- Minimum accuracy and minimum speed to continue (one `minimums` settings row and the palette; off by default; `minAccuracy`/`minWpm` in `src/profile.js`, any other stored value reads as off). Practice runs use the current minimums; a retest carries its baseline's, so both sides of a comparison pass the same filter; drills, custom text, the daily challenge, word practice, lessons, composing, races and ghost races always run to the end, and so does the standard test, a fixed measurement whose score a personal filter would lift (the minimum note stands aside while custom, composing or standard is on). Judged on the existing once-a-second live tick after a grace (5 s and 20 characters; for accuracy, enough characters that two misses alone can't cross the minimum: 40 at 95%, 100 at 98%), and on the final score at the end (the duration, the passage's last letter, or with quick end off a space submitting a wrong last word). A run the correction policy fails is reported as failed, never as under a minimum. A run stopped on the tick ends as interrupted with its reason ("Stopped: accuracy fell below 95%"); one that reaches its end below a minimum reads "Finished under your 98% minimum accuracy". Neither counts toward bests, trends, practice time or pattern evidence, and a retest that ends either way shows no comparison with its baseline (no score or target-timing deltas, no sample counts). After either, Space and Enter on Run again do nothing until the typist pauses (600 ms), so keys already in flight can't discard the result. After any run, focus goes to Run again (Start drill after a failed drill) only when it fits on screen below the score, clear of the dock; otherwise (1280×800 and phones) it goes to the result heading, so the score stays in view. Enter and the restart key work from either, with the same pause after a minimum stops a run. Minimums are a label on the run (conditions line, run card, Progress detail), not part of the conditions key: they never change the text, the input rule or the score.
- Per-user sessions. Everyone starts in guest mode: default settings, and nothing is written to storage. The person button (top right; `#account`) offers Create account, Sign in with Google and Sign in with email. Signed-in profiles are cached per user on the device (`stilltype-profile-v2:<user id>`) and synced to Supabase. Copies are merged, never replaced (`mergeSynced` in `src/account.js`): tabs merge each other's saves through the shared cache, and the account row is merged on load, when a tab returns to view or the connection returns, and before every push, which writes only if the row is unchanged since it was read. Changes from elsewhere never touch a run in progress: they apply when it ends, and newer test conditions replace only a practice passage nobody has started (keyboard focus stays where it was). A clear from elsewhere also withdraws, once no run is in progress, the baseline, drill and retest this tab offered for a run it removed. When two devices each tried a day's daily before merging, only the earlier try keeps its first-attempt label, and a try any copy labels a repeat stays one. Signing out first pushes whatever the device cache holds (other tabs' saves included) and clears the cache only once the account has it. A session that ends on its own (a refused refresh) keeps caching, and the next sign-in on the device merges those runs. The pre-accounts `stilltype-profile-v2` history is merged into the first account confirmed to have no saved profile; it stays in place if that check fails. Delete my account (account menu, or "delete account…" in the palette; typed `delete`, as with clear history) calls the `delete-account` Edge Function, which deletes the auth user; the profile, race rooms, race seats and friend rows go through ON DELETE CASCADE, and a trigger replaces the account's `rooms.opened_by` quota key. An account the Auth server reports as gone (a lost reply, any 5xx from the function or its gateway, or deleted elsewhere) counts as deleted; the function itself also looks the user up again after a failed `deleteUser` before answering 500. Only after it succeeds does the device drop the session, that account's cache, inbox and race reconnect credential, wipe history in memory (`wipeHistory`) and reload as a guest with a one-time notice; other open tabs hear the signed-out marker `forgetAccount` writes first (then the session and cache go, then the marker), save nothing more for the account and reload as guests once any run in progress ends. Any failure is explained in the dialog and changes nothing. The session refresh, the function call and the account check share one 30-second deadline (each request also gives up at the account service's 15-second timeout), so the dialog is never busy for longer; an account check the deadline cuts off is never taken as a deletion.

- Runs started (20 October 2026, `src/run-counts.js`): every run counts as started at the key that starts it (the moment `body[data-running]` turns on: practice, custom, code, daily, drills, retests, missed words, lessons and ghost races), whether it then finishes, is restarted, abandoned or failed by a correction rule or minimum; it counts as finished only when it ends as a counted run (status complete). - Learn to type (8 October 2026, `src/lessons.js`): a beginner path of 14 lessons that add keys a few at a time (f j, d k, s l, a ;, e i, r u, g h, t y, w o, q p, v m, b n, c x, z). Passages are real words from the existing word lists made only of learned keys; the first home-row lessons, where no such words exist, use key pairs labelled as "repetitions, not words". The on-screen keyboard becomes a split finger map during lessons. One completed run at 95% accuracy and the lesson's speed target (10–15 wpm) unlocks the next lesson; the numbers and met / not met are shown. Lessons teach physical-keyboard finger positions, so only a physical-keyboard run passes: a touch run is kept as a try labelled "touch input" and never unlocks (each record stores its input class; older records count as physical). Every run (lesson, practice, drill, retest, daily, custom) gets its input class in one place, `resetSession`, from the press that started it (`activationInput`, recorded on every pointerdown and on keys outside text fields before any handler runs): a tap or a pen press is touch, since it opens the soft keyboard (or a handwriting panel) without a tap on the passage; a mouse click or a key outside a text field is a physical keyboard; any key in a text field leaves it as it was, Esc included, since some soft keyboards have Esc (and Ctrl and Alt, so a chord is no proof either). After that, any touch while a run is prepared or running makes it touch (a palette command, a setting or the skip link can focus the input without starting a run). The cost is deliberate: on a touchscreen laptop, a tap and then hardware-keyboard typing (Esc restarts included) gives a touch run, a labelled lesson try that doesn't unlock and never a physical-keyboard best; so does a graphics-tablet pen on a desktop. The footer best, like the pace caret, is the one for the run's input class, and changes when a tap makes the run touch. Decided: no separate touch unlock track, since the Learn screen can't know the input class before a lesson starts. A newer account profile that locks the current lesson replaces it if it is waiting; a run already being typed finishes as not counted. A lesson result whose try the adopted profile doesn't hold (finished before the load-time check, which a newer row wins) is cleared rather than shown as passed. Progress lives in `profile.lessons` (guests: this tab only). A restart (Esc, palette, settings) never starts a locked lesson, and clearing history replaces a lesson session it locks. Lessons are their own kind: never runs, traces, bests, trends, retests, pattern evidence or seen text. Once every letter is in, the learn screen hands off to a practice run and the existing recommender → drill → retest loop. Entry points are the quiet "learn to type" link in the practice controls, the palette, and first-run links on Train and Progress. Decided: lesson time does not count toward the daily goal / streak or the break notice (both open PRs read `profile.runs`, which lessons never enter, and lesson progress stores no elapsed time). If the daily goal should count lesson minutes later, keep a small per-day seconds record in `profile.lessons` (`recordLessonRun`) rather than adding lessons to runs.
- Composing practice (9 October 2026): "compose" in the practice mode bar (or "composing practice" in the palette) swaps the passage for a neutral prompt and a free-typing field with no target text. It ends on Done, Ctrl/⌘+Enter or after 60 s from the first key. It reports free-typing speed (characters in the final text ÷ 5 per minute of active typing, each gap over 2 s counted as the average shorter gap) and backspace rate (backspace and delete keystrokes, held repeats included, ÷ all keystrokes) as their own measure: never compared with copy tests, never a best, kept out of runs, trends, retests and recurring evidence. Only the numbers are stored (`profile.compositions`, newest 100); the text never leaves the field, and the UI says so in one line. Progress lists recent sessions in their own section. Only single keys at the caret count: paste, cut, drop, undo, line deletes (⌘+Backspace), multi-character inserts and any key typed or deleted over a selection are refused, and a word deleted with Ctrl/⌥+Backspace counts as one deleting key. A key counts only when the field changed by exactly that key; IME or any other change (autocorrect, assistive text, an edit a refusal couldn't cancel) is unsupported input, and that, focus loss, the palette or leaving mid-way mean it isn't saved.

## Decisions to preserve

Afterimage is binding (see `AGENTS.md` and the Brand Commitments in `PRODUCT.md`): Literata for the passage and numerals, Geist Mono for small labels only; ten themes (dark and light follow the system until the user picks; eight more are picked by hand); one green accent for action, current state and the caret; opaque surfaces with no glass or glow; the fluid motion rule (motion is welcome mid-run when it helps, and scales to zero under reduced motion). The text-size preference keeps its stored values `22` / `28` / `36` (small / medium / large), mapped to the passage size in `src/styles.css`. Errors retain the non-colour tint; the wavy underline was removed on 29 September 2026. Every theme holds text at 4.5:1 and the caret, ghost caret, focus indicators and input outlines at 3:1, over mistyped-letter tints too (`tests/contrast.test.js`; disabled controls, the blurred handoff veil and the dimmed idle and unfocused caret are deliberate exceptions); the light accent, coral and ghost were darkened slightly and the placeholder became a token for this on 9 October 2026, so check that test before lightening any colour. The ghost pacer and speed graph are presentational and never scored. Keep metrics and conditions visible; never turn small-sample timing into a confident weakness or learning claim.

The correction policy defaults to free (`relaxed`), so mistakes can be typed through; stop on error requires mandatory correction, and no backspace, fail on word error and fail on any error are the stricter policies. Live metrics and the on-screen keyboard are also off by default. The selected correction policy is recorded in comparison keys, and retests restore the baseline policy. The keyboard layout is recorded the same way, but it is set in the operating system, so retests and drills never switch it: a baseline typed on another layout is refused for retest with a plain message, and drills from it stand alone. Touch runs keep the default (QWERTY) key, since the setting describes a physical keyboard, so a touch baseline is never refused or dropped for the layout. Only non-QWERTY layouts extend the key, and a missing layout always means QWERTY. Do not mix correction policies, quote difficulty/performance points or multiplayer ratings into personal skill progress. Existing unversioned `stilltype-best` data is not imported into comparable bests.

The newest 24 attempt traces (within a 2.5 million character trace budget, skipping oversized traces) and 1,000 compact run summaries (including drills, interrupted and daily runs) are retained per signed-in user; pattern counts remain only on the newest 120 summaries. Comparison summaries, seen-text IDs and bests remain until history is cleared. Everything uses the existing device cache and account `profiles.data` JSON. The friends board adds one nullable `profiles.board` column, the summary each save writes beside `data`; apply its migration before the frontend ships (until then each page's first save is refused once for the column and sent again without it). Old profiles derive available summaries from retained traces; missing dates and older comparison snapshots are labelled rather than fabricated. Clear/Undo covers all new history. Guests keep everything in memory only. Local two-player scores are transient. Online races store room state, chosen names, current typed text and score counters on the race service; guest reconnect credentials stay in sessionStorage for that tab. Online results never enter the profile. The footer's "suggest a feature" dialog inserts text and current view anonymously, never linked to an account; that table accepts inserts only and nobody can read it back through the public API. Storage failures are reported in result copy. Composing practice stores numbers only (`profile.compositions`, newest 100, rebuilt from known fields on load) and never the text; it is not a run kind, so bests, trends, retests, recurring targets, and run-based counts such as a daily goal or break notice leave it out. Account deletion is one authoritative server step (`auth.admin.deleteUser` in the Edge Function, hard delete); every new foreign key to `auth.users` must be ON DELETE CASCADE, or `supabase/tests/account-deletion.sql` fails. A user id kept any other way (like the `rooms.opened_by` quota key, cleared by the `forget_race_opener` trigger) needs its own cleanup and its own case in that test. The client clears nothing until the function confirms.

The practice screen is anchored, not centred on its content (21 October 2026): it starts where open practice's block (`--practice-block`) would start if centred, and every mode keeps that top, so the rail never moves and time, words, quote, code and standard start the passage on the same line. The standard recipe hangs under the controls from 761px and takes the lengths' row on phones for that reason; anything new under the rail must take no height of its own in those modes. `e2e/layout.spec.js` checks the rail and the passage across modes at 1280×800, 390×844 and 320×568. Under 361px a lesson's name drops to the title size so its passage starts above the bottom dock at 320×568 (also checked there).

A slow reply never acts over what the person did meanwhile. A Race compares where it was clicked with where the person is when its reply lands (`raceContext` in `src/app.js`, which counts anything typed since, in the passage or any field) and otherwise only offers the race (`inbox.offer`); add a field there for any new place a race could open over, rather than clearing the request in each code path. A toast acts only for its inbox entry as it stands now. `announce` reads messages from the same moment together, so a toast held until a run ends is heard beside the run's result.

Sync merges copies of the profile: attempts, runs and loops by id (date order, then the usual caps), the higher best, seen passages by union, and each setting from its latest change (`preferencesAt`). Ties (an equal best, undated records, two different picks of a setting with the same stamp) break the same way on every copy, so copies settle. Runs started and finished (`runCounts`) are `{ [counter]: { [day]: [started, finished] } }`: each page load mints its own counter the first time it counts a run and only that tab writes it, so its numbers only grow and copies merge exactly by the larger of each number (`mergeRunCounts`), however many tabs and devices count at once and however often a copy is merged again. A clear empties it, and a copy that hadn't applied the clear loses its days through the clear's own, as `practiceDays` does (so starts made on the clear's day by a device that hadn't yet heard of it are lost, the same trade-off); Undo restores it with everything else. A tab whose counter's numbers a clear took (here or merged in) mints a new counter rather than count up again from what the clear left, so an Undo or stale copy holding the old, larger numbers can never hide the new runs. Only the newest 730 counted days are kept, as for the archive. Clearing history leaves a `historyClearedAt` marker (the clearing device's now, then `~` and a random id: the marker is the clear's identity, and two devices can stamp independent clears the same millisecond; records stamped after it by a clock running ahead are named in `historyClearedIds` as `[marker, id]` pairs, all kept for every clear not undone, uncapped, since a newer clear can't name what an older one already removed; a clear also names, under its own marker, every record the clears it knows of had named, as each was made before it, so an older clear's undo arriving later can't bring one back past it) so a copy that missed the clear can't bring it back, even after a newer clear from a device that never held the record. Undo records that marker as undone so it never applies again (`undoneClears` is never trimmed), and restores what the clear removed from every copy merged since: each tab keeps, per clear still in force, the copies that clear removed history from, by its date or by a record it named (an older clear's names can arrive under a newer marker the copies already share), side by side (`mergeAndHold`; merging them would apply one copy's clear to another). Each list goes back only with its own clear's undo, so a newer clear never drops what an older one holds, and what a clear still in force removes from them is held again under that clear. Each copy also keeps the older clears still in force that it has applied (`appliedClears`) and those it has only heard of (`heardClears`). A copy that applies a clear holds nothing from before it, whatever a later run's stamp, so once its newest marker is undone it still answers to the older clears it had applied, and, as one that never applied them, to those it only heard of; no clear still in force is forgotten. Where a clear takes a best (by date or by name), that copy's surviving practice runs set the best again, and a passage shown only by records a clear named loses its seen mark. Builds from before merging synced whole copies (the copy saved later replaced the other) and cleared history by saving an empty copy, with no marker. This build writes `mergeStamp` with every `updatedAt` (`stampProfile`); an older build stamps `updatedAt` and passes `mergeStamp` through, so a copy whose two differ was last saved by an older build. In a merge the copy saved later wins, as whole-copy sync chose, but only over what predates its history: its start (`legacyClearedAt`) is its earliest record or best when an older build saved it last, and otherwise the start it carried from the last such copy merged. The copy saved earlier, if its own start is earlier, drops its history and bests from at or before that start (seen marks as for a clear it hadn't applied, and no Undo); the rest of it, which whole-copy sync dropped too, stays. So a clear made on an older build stands wherever that build's sync kept it, and a copy from before it that turns up later (another device's older cache) is held to it; a save made later by a copy that never heard of it, on either build, replaces it, as it did there. Writes are conditional on the row's `updated_at` (`PATCH … updated_at=eq.<seen>`); a lost race reads, merges and retries. Requests to the account service give up after 15 s (`REQUEST_TIMEOUT_MS`, never for the keepalive write of a hidden page) and count as offline, so edits stay and sign-out can't hang. A tab still holding an account that another tab has signed out of never refreshes it; a refused refresh removes only the session whose token was refused, and a refresh is stored only over the session it refreshed. A sign-out ends the account's sign-in on the device as it stands when the sign-out is asked for, including a newer one that another tab made with no sign-out between (a guest tab signing in), so every tab of the account signs out, as tabs sharing one sign-in do. Each sign-in carries an id that its refreshes keep (`signInId`), so a sign-out removes the session and cache only while the device still holds that sign-in, and a sign-out another tab overtakes while it waits on the network (a sign-out there, or a sign-in as anyone, the same account included) stops and starts again as the device now is, sending no logout (Supabase's logout ends every session of the account). None of these can end a sign-in made after the sign-out was asked for, or another account's. Other tabs follow a sign-out either way: one that keeps unsent edits for the next sign-in leaves a `stilltype-signed-out:<user id>` marker until that user signs in again, and one that sent everything removes the device cache. They then save and send nothing more for the account and, once any run in progress ends (that run is kept in memory only), reload as the device now is: a guest, or whoever has signed in since (the same account included), so only edits made before the sign-out reach the account. A sign-in as another account is followed the same way. A session that only expired (a refused refresh removes the session and nothing else) is not followed: its tabs keep caching for the next sign-in. Tabs share no lock, and reads of the device cache across tabs can be milliseconds stale (Web Locks don't change this in Chrome), so no write may lose another's. Cache writes are unions: a tab that takes in a copy lacking something it holds writes the union back, and a pull that finds the row lacking something this tab holds (another tab's unsent run included) pushes it. A sign-out's removal of the cache is named and repairable: one that sent everything first writes a `{ sent }` marker stamping the copy it sent (`textStamp`), then removes the session and the cache; a tab that hears the removal of a copy that wasn't the one sent puts it back for the next sign-in (`restoreUnsent`, from the last copy that tab saved, or took in holding all it had saved, never from memory, so a run finished after hearing of the sign-out stays out). An explicit pick of a setting is stamped even when it matches what is shown (`saveChoice`: the test shape, word list, theme, text size, pace caret with its custom speed when that speed was on show (picking custom from another pace leaves a speed chosen elsewhere alone), and the custom text with its order), so it outranks a different value waiting from elsewhere. A drill or retest runs at its baseline's conditions without recording them as a settings change, so the saved settings (a pick made elsewhere meanwhile included) return when it ends; practising a target from Progress or Train no longer switches practice to that target's conditions afterwards. Limits: settings and clears are ordered by device clocks; seen passages carry no date, so a passage displayed but never typed on a device that hadn't yet heard of a clear loses its seen mark (typing it afterwards, even in an interrupted run or a daily attempt, marks it again); the cache repair needs a tab of the account to hear the removal, so a save is lost only if its tab closes within milliseconds of it with no other tab of the account open, or if two different saves are each removed unseen and their repairs collide; a run saved within milliseconds of a sign-out, by a tab that hasn't yet heard of it, reaches the account at the next sign-in; a sign-out or refresh landing within milliseconds of a sign-in in another tab can undo that sign-in, though no history is lost; and what a tab holds for Undo lives in memory, so a device that reloads between a clear and its undo can't give back its own unsynced runs from before the clear.
