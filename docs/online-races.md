# Private online races

Implemented 30 September 2026 using the existing Supabase project and static native JavaScript app.

## Player flow

Open Challenge and sign in to host. Enter a race name and either an existing account email or leave the email blank for a guest link. Account invitations appear in the recipient’s Challenge inbox, refreshed every ten seconds while open; no email is sent. The response does not reveal whether an email belongs to an account. Guest links admit one opponent without requiring a Supabase anonymous-auth session.

Both players ready up. The server schedules a shared five-second countdown and a race lasting up to sixty seconds. Completing the passage correctly can finish a player early. Progress is exchanged about every 650 ms, outside the local keystroke/render path. The server computes matching retained characters, elapsed race time and WPM; accuracy uses bounded insertion/error counters. Results remain friendly and unranked: browser data cannot establish that a human typed it.

The invitation expires fifteen minutes after room creation. Leaving cancels an active room for both players. A disconnected player’s seat remains held; the client retries automatically. Reload restores the last server-acknowledged text and counters. A ten-second final-packet grace period keeps elapsed time capped at sixty seconds and allows delayed results to arrive. A player who does not return is finalized from their last acknowledged progress. A new race requires a new room.

One keyboard retains the original local challenge. Online races do not add attempts, personal bests or learning comparisons. Revealed quote IDs do enter seen-text tracking so they cannot later masquerade as fresh retests.

## Friends, rematches and the inbox (7 October 2026)

- **Friends.** Each signed-in host keeps a private friend list on the race service (`race_private.friends`). Inviting an account by email saves that email to the list by default ("save to friends"). After a race against another account, "Add <name> to friends" saves them without ever revealing their email or account id; the row only says "raced before". The host who invited someone by email is not offered this, since they already have them by email. Challenge on a friend row creates an account invitation exactly as typing the email would, with the same non-revealing reply. Lists are capped at 100 and are not mutual: adding someone tells them nothing.
- **Race again.** Any finished, cancelled or expired race with two players offers Race again. The first player to ask opens a new room with the same host, seats, names and settings and a fresh passage of the same length and difficulty; the second player's Race again (shown as Join rematch) joins that room. Accounts keep their seat by account and a guest keeps the same seat capability, so nobody re-enters an email or a link. Both players still press Ready. A closed room is watched every three seconds while it is open, so a rematch request reaches a guest without an inbox.
- **Toast and inbox.** Signed-in players get an envelope next to the account button. Invitations are polled every ten seconds on every screen (paused while the tab is hidden or a run is in progress). A new invitation or rematch request shows a toast at the top right that leaves after 18 seconds, held while hovered or focused; a toast that arrives mid-run waits until the run ends. The inbox lists invitations and rematch requests (with Join), an opponent arriving while you are on another screen (with Open) and race results (with Race again). Open only works while that race is still live in this tab, and Race again lapses 23 hours after the room's expiry, before the service deletes the room; lapsed entries stay listed as closed. Entries are kept per user on this device only (`stilltype-inbox-v1:<user id>`, newest 30) and removed on sign-out. Guests see rematch toasts but keep no inbox.

The migration is `supabase/migrations/20261007031500_race_friends_rematch.sql`; `supabase/tests/race-friends-rematch.sql` covers friend privacy, friend invites, rematch seats and guest rematches. Both SQL test files pass against the two migrations on PostgreSQL 16 with a minimal `auth` / `extensions` stub. Apply the migration before shipping the frontend: until then friends and Race again report that they are being set up.

## Friends board (9 October 2026)

- **Sharing is opt-in.** Nothing of yours is shown until the account turns on "share on friends board" (the switch on the board, or the palette command); it is off by default, including for friend pairs that existed before the board. Whether an account shares is recorded only by its membership on the service, and every board reply says so; it is not a synced preference (a `shareBoard` field saved in a profile by an earlier build is dropped). Each device keeps what it last read or chose, with the sharing version of the reply that said so (`stilltype-board-sharing:<account id>` in localStorage: `1` or `0`, then `:` and the version; removed on sign-out), only to show the switch and to send that version with a share. A device new to the account reads the board once after the account check to learn it; until it has, the switch shows off without the "not sharing" line. Only the switch shares: learning from a reply that the account shares just shows the switch on. While it is off the board shows nobody's rows, yours or friends', and says so in one line beside the switch. Turning sharing off takes you off the board at once: friends no longer see your row from their next read. Your summary stays only in your own owner-only profile row, beside the history it is counted from. Turning it on again shows your row as your profile row holds it. An opt-out the service hasn't confirmed (offline, or a service error) is kept on the device (`stilltype-board-optout:<account id>` in localStorage) and sent again before any other board request, turning sharing back on included, on the next board read or page load, until the service confirms it. Until then that device's profile saves write no summary (`board: null`), so it shows nothing new, and it accepts no sharing state from the service. Each kept opt-out has its own id, and a confirmation settles only the one it was sent for, so a slow reply to an older opt-out can't drop a newer one made after sharing was turned back on. The id travels with the opt-out (`{"id": "…"}`), and the service keeps the id of the last opt-out it applied, through any shares after it, so the same opt-out arriving again changes nothing. An opt-out whose reply was lost, sent again before turning sharing back on, is answered as done without moving the sharing version a second time, and the share after it counts at the first click; a copy that was slow on its way (another tab sent it too) and lands after that share leaves the share standing, since the share was sent after the opt-out was applied. An opt-out is sent only with the id it is kept under, and only while it is still kept: a board request (Refresh, a reconnect, the re-read after a profile save) that waited behind a share which confirmed it sends nothing more and just reads the board. Where the browser can't keep it in localStorage, the page keeps it until it is confirmed. Turning sharing on again rewrites the summary of the row as it stands (the same conditional repair as on load), so saves made while an opt-out was unconfirmed don't leave the row reading as nothing yet. Every tab of the browser hears of it at once (a `storage` event) and stops too, and any tab sends it with its next board request; the service answers a repeat as done. The tabs also share what the device last read about sharing: a board open in one tab shows the switch on at once when another tab turns sharing on, and reads again to show the rows. Another device that reads the board meanwhile sees the account still sharing and shows sharing on, but never shares by itself; once the opt-out lands, its next read says sharing is off, and it says so in one quiet line.
- **Changes to sharing apply in order, account-wide.** The service keeps a sharing version per account (`race_private.board_sharing`, a counter that outlives turning sharing off), moves it on by one with every share and opt-out it applies, and returns it in every reply (`sharingVersion`). An opt-out always applies, and moves the version on even when the account is already off the board; only the same opt-out arriving again (by its id) changes nothing, whether or not a share was applied since. Sharing state only moves forward on a browser: a reply, or a value another tab kept, counts only if its version is newer than any this browser holds (the tab's own or the one its tabs keep). So a slow board read answered before another tab turned sharing on, arriving after this browser learned of it, changes neither the switch nor what the tabs keep, and a reply at the same version changes nothing. A share is sent with the version its tab last read (`{"version": n}`) and applies only if the account is still at that version; otherwise it is refused, changes nothing, and the reply says whether the account shares. So a share made before another device's opt-out can never undo it, however late it arrives: the switch that sent it stays off and says "Sharing was turned off on another device.", and turning it on again from there (now based on the version that reply gave) shares. A share is never sent blind: a tab of a browser that has read no version reads the board first. The version a tab sends is the one in the last board this browser showed: the tabs keep it beside whether the account shares, in one value, so a tab whose switch follows another tab's change adopts that change's version with it, and sharing turned off in one tab and back on in another shares at the first click. While a tab's own share is waiting to go, nothing moves the version it will send but the tab's own opt-outs and shares ahead of it, one step each: a reply, or another tab's change, that arrives meanwhile doesn't count, since it may hold an opt-out made after the switch moved. So a share waiting behind this device's own opt-out is refused if any other change landed in between, and a share waiting in one tab is refused after an opt-out made later in another. The reverse order is the safe way round: an opt-out that arrives after a newer share turns sharing off, and the account can switch it back on. Two devices that turn sharing on from the same version both end up sharing (the second is refused but its reply says the account shares).
- **Retention.** The summary holds the daily results of the latest two days and the practice totals of the latest two weeks found in the runs, rewritten in the account's own profile row with every profile save; the board shows only the service's own today and this week, so an older one reads as nothing yet. It is counted from the runs the profile keeps, its newest 1,000 comparable runs: past that many runs in one week (about four hours of 15-second tests) the oldest of the week's runs leave the profile, and the week's practice time and run count fall with them, as Progress's weekly count does. Turning sharing off ends the membership, and deleting the account deletes the membership and the profile row (`on delete cascade`).
- **What it shows.** Challenge → Friends lists you and your mutual friends who share twice: today's daily challenge (each person's best completed physical-keyboard attempt for today's UTC date, with how many completed attempts) and this week's practice (completed, uninterrupted runs since Monday 00:00 UTC, with the run count; the runs' time is summed, then floored to whole seconds, so it is never rounded up). Custom-text runs count in neither: they are never compared, Progress counts none of them, and they are kept on their own budget of 50, so a custom run adds no practice time or run to the week and is never a daily result. Both are ordered among the people shown and nowhere else; there is no public ranking. Guests see a sign-in prompt and have no row.
- **Who sees whom.** A row is shown only to mutual friends, and only while both of you share: you see someone when each of you has the other on your friend list, by account (added after a race) or by a confirmed email (resolved exactly as a typed invite is). One-way adding shows nothing, so typing an email never reveals whether it has an account or anything about it unless that account chose you too. Removing someone from your list hides you from them and them from you. Rows carry no name, email or account id; each reader labels a row with the name on their own list.
- **Where the numbers come from.** The board shows exactly what each account's profile row holds. Every profile save writes the summary of exactly the copy it saves into the row's `board` column (with `v`, the summary's shape), stamped `at` with that save's own `updated_at`, and the service shows a summary only while `at` is still the row's `updated_at`. The summary files each run under its own day and week, from the run's own record, as the Daily panel and Progress do: `days` keys each daily result by the UTC date it was played for, and `weeks` keys practice by the Monday (00:00 UTC) of the week each run was made in. The service reads the entries for its own today and week, so no device's clock, the writer's included, decides which day or week a run counts in: a laptop running ten minutes slow that saves just after midnight still shows the new day's daily and week. A save by a build that doesn't write the column moves `updated_at` and so hides the old summary, rather than letting it describe another copy. A load that writes nothing itself repairs a row whose summary doesn't describe it (written before the column existed, by an older cached build, or in an older shape) from that row's own data, with a PATCH that only applies while the row's `updated_at` is still the one it was counted from. The board itself only reads. It keeps no clears, undos, clocks or queue of its own: a history clear or its undo is a profile save like any other. Sync on master is last-writer-wins, so a stale device's save that puts cleared history back in the row puts it back on the board too, exactly as in Progress; #57's merging sync fixes both at the source. A board left open reads again `nextDay` seconds after a reply arrived (the service's seconds to its next 00:00 UTC), so neither this device's clock nor the reply's travel time can make it read early. That deadline is kept on both the device's clock and the page's monotonic clock, and whichever passes first triggers the read, so a clock set back while the board is open can't hold it back either. If the project has no `board` column yet (PostgREST's PGRST204) or its check refuses a summary, the save goes again without it and the page leaves it out until it reloads, so the board can never stop the profile syncing. Each daily result carries its version (the daily conditions key, which includes the corpus and metric version, and the passage); a reader on another build sees it as "another version of the daily · not compared" rather than ranked. The service shows only what a browser writes within (for today's UTC date, a printable version of at most 200 characters, 0–400 wpm, 0–100% accuracy and 1–1000 attempts; for this UTC week, at most a week of seconds and 10,000 runs), each part checked on its own, so anything else, including a malformed column an owner wrote over the API, reads as nothing yet and never fails the board. The numbers are reported by browsers and are not verified; they never enter progress or bests.
- **Storage.** `public.profiles.board` (nullable `jsonb`, an object of at most 16 KB) holds each account's summary beside its `data`, under the row's existing owner-only RLS and grants. `race_private.board_members` holds one row per account that shares (RLS on, no browser privileges). `race_private.board_numbers` reads a summary for the board (the stamp first, then each part; it never raises). `race_private.board_sharing` holds each account's sharing version and the id of the last opt-out it applied, kept through the shares after it (RLS on, no browser privileges); every share or opt-out applied moves the version on by one under that row's lock, so changes to one account apply one at a time, and a second copy of one opt-out waits for the first and then finds it applied. `public.friends_board` is an invoker wrapper, granted to signed-in accounts only, around the definer `race_private.board`, whose only actions are `board`, `share` (applied only when sent with the account's current version as a whole number; anything else is refused without raising) and `unshare` (never refused; sent with its opt-out's id, `{"id": "…"}` of 1–64 letters, digits, `-` or `_`, so a repeat applies once and changes nothing, even after a share; without a valid id it is a new opt-out, which leaves the last id as it was). No numbers travel through it and it writes no profile row; it builds the reply, `{date, weekStart, sharing, sharingVersion, nextDay, rows}`, with `race_private.board_snapshot`, which tells a reader only their own sharing state and version.

The migration is `supabase/migrations/20261009120000_friends_board.sql`; `supabase/tests/friends-board.sql` covers privileges (including the column's and the versions'), guests, opt-in membership (nothing shown before it, nothing shown after it, sharing again), the order of changes (a share sent before a newer opt-out is refused and leaves the account off the board, an opt-out always applies and moves the version on, a share without the current version as a whole number is refused without raising, two shares from one version, versions deleted with the account), repeated opt-outs (the same id again changes nothing and the share after it counts, and a copy of it landing after that share leaves the share standing; a new id, also while already off the board, and any missing or malformed id each move the version on, without raising, and one without an id leaves the last id as it was), binding a summary to its row (a save without the column hides it, a repair from another version changes nothing, a stamp in the API's own format or another offset still matches), each part's limits on its own, the entries for the service's own day and week chosen among several, forged and malformed columns that read as nothing yet without raising, the column's check, other accounts unable to read or write a row, a member with no profile row, one-way and mutual lists, unconfirmed emails, duplicate list entries, stale days and weeks under a non-UTC session time zone, `nextDay`, removal and account deletion. All three SQL test files pass against the five migrations on PostgreSQL 16 with the minimal `auth` / `extensions` stub. The board test makes every call and profile write the way PostgREST does, as the `authenticated` role with the user's id in the JWT claim (as `anon` for a guest), so a missing grant on the path fails it. **Apply the migration before shipping the frontend**: until then the board reports that it is being set up, and each page's first profile save is refused once for the missing column and sent again without it.

## Storage and access

- `src/multiplayer.js` calls `public.race_action` using the existing browser publishable key and a member token when signed in. It refreshes sessions and maintains progress sequence numbers across reloads.
- `race_private.rooms` and `race_private.players` enable RLS and grant browsers no table privileges. An explicitly granted invoker RPC calls a private definer function that checks account membership or an independent guest-seat capability on every operation. Transitions lock the room row; hosting quotas serialize by account. A rematch counts against the racer who asks for it (their account, or a guest's seat), not the original host.
- Account lookups stay inside the database. Snapshots omit account IDs, emails, capability hashes and the other player’s typed text/counters. Both players can see names, readiness, progress and scores.
- A guest invitation and the joined guest’s seat use different random 256-bit capabilities. Only hashes are stored in the database. Invitation capabilities live in URL fragments; joined-seat credentials and the host’s link are retained only in the current tab’s sessionStorage, along with any pending invite needed through sign-in redirects. Solo guest history is still not persisted.
- Room data includes current typed text, counters and scores. Creating a room opportunistically removes rooms whose expiration was more than a day ago; there is no scheduled deletion guarantee while the app is idle.
- Deleting an account (`supabase/functions/delete-account`) removes its race rows through the foreign keys to `auth.users`: rooms it hosts or was invited to, its seats in other players' rooms, its friend list and its place on other lists as a raced friend. An email someone else typed into their own friend list stays there and no longer matches an account. A rematch room it opened in someone else's race stays, as that racer's room; a trigger (`supabase/migrations/20261009140000_forget_deleted_race_opener.sql`) replaces the deleted account's quota key (`opened_by`) with `deleted`.

The migration is `supabase/migrations/20260930085227_online_races.sql`, applied to project `bicbyljexprkaedakofa` (`typingsite`) as remote migration `20260930085736`. No new runtime dependency or WebSocket server is required. The static frontend build uses the existing hosting workflow; this change does not publish a frontend deployment.

## Verification

The build and all four Node test files pass. The 48 Chromium scenarios pass across the full regression run and the final targeted rerun of the updated reduced-motion assertion. Desktop dark and 320 px light lobby screenshots were visually reviewed.

`npm test` covers existing scoring/accounts plus transport payloads, fragment parsing, capabilities and reconnect sequencing. `e2e/multiplayer.spec.js` drives independent browser contexts against shared in-memory Supabase state: full race/results, account inbox, host/guest reload, mid-race progress restoration, cancellation, occupied links, expiration, offline recovery and 320 px layouts in both themes. The fake is for browser orchestration, not proof of database security.

`supabase/tests/online-races.sql` was separately executed against the deployed database. It creates temporary test users inside a transaction and rolls everything back. Assertions cover host authorization, unauthorized readers, guest capability isolation, pre-start rejection, impossible counters, incomplete early finishes, server scoring, stale updates, account invite isolation and cancellation. Catalog checks confirmed both private tables have RLS and no browser read/write privileges.

The Supabase security advisor reports informational [RLS without policies](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) for these intentionally inaccessible private tables. An existing project-level [leaked-password protection setting](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) is unchanged.

Browser verification uses Chromium. Real cross-region latency, physical mobile keyboards and full anti-cheat remain unmeasured. Public matchmaking, ratings and email delivery are outside this feature.
