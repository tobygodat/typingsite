# Private online races

Implemented 30 September 2026 using the existing Supabase project and static native JavaScript app.

## Player flow

Open Challenge and sign in to host. Enter a race name and either an existing account email or leave the email blank for a guest link. Account invitations appear in the recipient’s Challenge inbox, refreshed every ten seconds while open; no email is sent. The response does not reveal whether an email belongs to an account. Guest links admit one opponent without requiring a Supabase anonymous-auth session.

Both players ready up. The server schedules a shared five-second countdown and a race lasting up to sixty seconds. Completing the passage correctly can finish a player early. Progress is exchanged about every 650 ms, outside the local keystroke/render path. The server computes matching retained characters, elapsed race time and WPM; accuracy uses bounded insertion/error counters. Results remain friendly and unranked: browser data cannot establish that a human typed it.

The invitation expires fifteen minutes after room creation. Leaving cancels an active room for both players. A disconnected player’s seat remains held; the client retries automatically. Reload restores the last server-acknowledged text and counters. A ten-second final-packet grace period keeps elapsed time capped at sixty seconds and allows delayed results to arrive. A player who does not return is finalized from their last acknowledged progress. A new race requires a new room.

One keyboard retains the original local challenge. Online races do not add attempts, personal bests or learning comparisons. Revealed quote IDs do enter seen-text tracking so they cannot later masquerade as fresh retests.

## Friends, rematches and the inbox (7 October 2026)

- **Friends.** Each signed-in host keeps a private friend list on the race service (`race_private.friends`). Inviting an account by email saves that email to the list by default ("save to friends"). After a race against another account, "Add <name> to friends" saves them without ever revealing their email or account id; the row only says "raced before". The host who invited someone by email is not offered this, since they already have them by email. Challenge on a friend row creates an account invitation exactly as typing the email would, with the same non-revealing reply. Lists are capped at 100 and are not mutual: adding someone tells them nothing.
- **Race again.** Any finished, cancelled or expired race with two players offers Race again. The first player to ask opens a new room with the same host, seats, names and settings and a fresh passage of the same length and difficulty; the second player's Race again (shown as Join rematch) joins that room. Accounts keep their seat by account and a guest keeps the same seat capability, so nobody re-enters an email or a link. Both players still press Ready. A closed room is watched every three seconds while it is open, so a rematch request reaches a guest without an inbox.
- **Toast and inbox.** Signed-in players get an envelope next to the account button. Invitations are polled every ten seconds on every screen (paused while the tab is hidden or a run is in progress). A new invitation or rematch request shows a toast at the top right that leaves after 18 seconds, held while hovered or focused; a toast that arrives mid-run waits until the run ends. The inbox lists invitations and rematch requests (with Join), an opponent arriving while you are on another screen (with Open) and race results (with Race again). Open only works while that race is still live in this tab, and Race again lapses 23 hours after the room's expiry, before the service deletes the room; lapsed entries stay listed as closed. Entries are kept per user on this device only (`stilltype-inbox-v1:<user id>`, newest 30) and removed on sign-out. Guests see rematch toasts but keep no inbox.

The migration is `supabase/migrations/20261007031500_race_friends_rematch.sql`; `supabase/tests/race-friends-rematch.sql` covers friend privacy, friend invites, rematch seats and guest rematches. Both SQL test files pass against the two migrations on PostgreSQL 16 with a minimal `auth` / `extensions` stub. Apply the migration before shipping the frontend: until then friends and Race again report that they are being set up.

## Friends board (9 October 2026)

- **Sharing is opt-in.** Nothing is published until the account turns on "share on friends board" (the switch on the board, or the palette command); it is off by default, including for friend pairs that existed before the board. Whether an account shares is recorded only by its row on the service, and every board reply says so; it is not a synced preference (a `shareBoard` field saved in a profile by an earlier build is dropped). Each device keeps what it last read or chose (`stilltype-board-sharing:<account id>` in localStorage, removed on sign-out) only to show the switch and to know when to publish before its next board request. A device new to the account reads the board once after the account check to learn it; until it has, the switch shows off without the "not sharing" line. A device shares only when its own switch is turned on: learning from a reply that the account shares only lets it publish into the row already there, and learning that it doesn't stops it publishing. While it is off the board shows nobody's rows, yours or friends', and says so in one line beside the switch. Turning it off empties your row on the service down to a marker with no numbers, so friends stop seeing you at once and a browser that missed the change can't share again (its next publish is refused, and that tab turns its own switch off with one quiet line on the board). Turning it on again shares the tab's current summary. A switch made before the page's first account check waits for the check, then shares the summary the check settles on. An opt-out the service hasn't confirmed (offline, or a service error) is kept on the device (`stilltype-board-optout:<account id>` in localStorage) and sent again before any other board request, on the next board read or page load, until the service confirms it; until then that device publishes nothing and accepts no sharing state from the service. Every tab of the browser re-reads it before publishing and hears of it at once (a `storage` event), so a sibling tab stops publishing too, and any tab sends it with its next board request (a run there included); the service answers a repeat as done. The tabs also share what the device last read about sharing: a board open in one tab shows the switch on at once when another tab turns sharing on, and reads again (only reads: its own summary goes with its next run or Refresh) to show the rows. Another device that reads the row meanwhile sees it still sharing, shows sharing on and may publish into it, but never shares it again; once the opt-out lands the row is a marker, and that device's next publish is refused and it stops too.
- **Retention.** Only today's daily result, this week's practice total and the account's best on each of up to 16 test shapes (its speed, accuracy and the UTC day it was set) are kept, one row per account that shares; each new day or week replaces the last day's or week's numbers. Bests stay until a history clear, which replaces them with those set since (none, at the moment of clearing); an Undo of the clear puts them back. Turning sharing off removes the numbers, bests included, and deleting the account deletes the row (`on delete cascade`).
- **What it shows.** Challenge → Friends lists you and your mutual friends who share three times: today's daily challenge (each person's best completed physical-keyboard attempt for today's UTC date, with how many completed attempts), this week's practice (completed, uninterrupted runs since Monday 00:00 UTC, with the run count) and Bests (each person's best on one test shape, with its accuracy and date). All three are ordered among the people shown and nowhere else; there is no public ranking. Guests see a sign-in prompt and publish nothing.
- **Bests.** A best comes only from a run that can set a personal best in the app: a completed, uninterrupted practice test or retest on a timed, word-count or quote test. Drills, dailies, races, interrupted runs and any other kind never count. Each is keyed by the run's condition key (mode, length, punctuation or quote filters, word list, input, correction policy, corpus and metric version) and is the fastest run on it, then the more accurate, then the earlier, dated by the UTC day it was set on the service's clock (offset by the latest reply's `now`; a tab that hasn't heard from the board since it loaded reads it once, quietly, before its first write, so a device clock that runs ahead never dates a best past the service's tomorrow). A browser sends at most 16 shapes: the ones this build compares first, then the ones it has the most runs on (then the most recently run). A run dated outside the service's limits on the service's clock (stored while a device's clock was far off) is left out, so it can never get a write refused. The section has a labelled native select ("Test conditions") naming each shape by its length and text first, then whatever else tells the listed shapes apart (a quote's missing word list doesn't count; two quote shapes whose keys differ only by the punctuation setting, which quotes ignore, read "punctuation on" or "off"); it opens on the shape you have the most such runs on (then the one most people have a best on) and keeps your pick for the tab. A line under it gives the full conditions. People are ranked by wpm, accuracy breaking a tie; someone without a best on that exact key reads "no best on this shape yet". Only bests on exactly the picked key are compared: a key from another build (another corpus or metric version, or a key this build wouldn't write: a length, word list, quote length or difficulty, input or correction policy outside the app's own options, or a part filled in that its mode doesn't have) is never listed, and a best on the same shape from another build reads "another version of this shape · not compared".
- **Bests and history clears.** Bests are computed from the browser's run summaries since the board's latest clear, the same runs as the week's practice, not from the profile's stored bests, which carry no accuracy and follow the profile's own history rather than the board's clear. Counting the run summaries since the clear, as the week already does, makes bests go through the clear protocol exactly as the week does. (A profile keeps its newest 1,000 run summaries, so a best older than those is no longer counted.) A publish folds them in (on each shape the better best stays, and past 16 shapes the ones just sent stay, then the most recently set), since a tab's bests are a lower bound. A clear replaces them with the clearing tab's bests since it happened (none), so the cleared bests come off friends' boards. Its Undo replaces them with the restored history's bests since the clear before, which brings them back. A browser that missed the clear is refused and resends only its bests since the clear; a clear repeated after being overtaken changes nothing; an undo of a clear that is no longer the latest is refused. The service also keeps no best dated before the UTC day of the row's latest clear (less a day's grace for the browser's clock), and turning sharing off empties them with the rest of the row. The service accepts at most 16 shapes, keys of letters, digits, colons, dots, underscores and hyphens up to 200 characters, whole wpm of 0–400, whole accuracy of 0–100, and a date from 1 January 2026 (before Stilltype existed) to tomorrow (UTC).
- **Who sees whom.** A row is shown only to mutual friends, and only while both of you share: you see someone when each of you has the other on your friend list, by account (added after a race) or by a confirmed email (resolved exactly as a typed invite is). One-way adding shows nothing, so typing an email never reveals whether it has an account or anything about it unless that account chose you too. Removing someone from your list hides you from them and them from you. Rows carry no name, email or account id; each reader labels a row with the name on their own list.
- **Publishing.** While sharing, the signed-in browser computes its own summary from its profile and sends it after each run, history clear or undo made in that tab (about 1.5 s later, never mid-run), skipping an unchanged publish; a clear or undo is always sent, since another tab or device may have raised the stored numbers since. A change made before the page's first account check, or one that failed, stays pending and is sent after the check and when the browser comes back online. Opening the board (and its midnight re-read) also sends the tab's summary when it differs from the last one that tab sent, so history loaded from the account reaches the board without a new run; an unchanged summary is only read. A tab's summary is a lower bound, since another tab or device of the account may hold runs it never saw, so the service folds each one into the stored row instead of overwriting it: the stored daily result stays unless the new one is for a later day (today's before any other) or is better on the same daily (faster, or as fast and more accurate), the larger attempt count stays, and within one week the larger practice time and run count stay. A daily from another build replaces the stored one, since the two are never compared. A history clear and its undo send `replace` instead, which overwrites the row so the numbers can go down. The row also records the latest history clear on any device: an id the clearing tab makes, and the time runs count from, on the service's clock: when the clear happened, however late the request arrives. The tab sends when it cleared and when it sent the request, both by its own clock, and the service lays that gap back from its own clock on arrival, so a device clock that is off doesn't matter, only network delay. It is never later than now. A clear takes effect when it happened after the latest one; one that happened before it (it waited offline, or another tab's went first) is answered as done and changes nothing, so its runs, counted from before the latest clear, never come back. The row keeps the clear before the latest for an undo. A clear or undo repeated after a lost reply is answered as done, so retrying never loses the clear an undo should put back. While that clear is still the latest (or the undo was taken), what it sends, the runs since the clear it leaves in place, is folded in like a publish, so runs made before the retry still count. A clear overtaken since (by a newer clear, or by its undo) changes nothing at all: the row remembers its last twenty clears, and a retry of one of them never becomes the latest again or brings back runs a newer clear removed; the tab then sends its runs since the newer one. A clear or undo is kept and sent whatever the device last read about sharing (another device may have turned it on since): the service refuses it, changing nothing, when the account doesn't share, and only that settles it; taken, it tells the device the account shares. While an opt-out is unconfirmed it waits, and is dropped when the opt-out lands (the row is a marker) or sent after the share when sharing is turned back on. Publishing and turning sharing on name the latest clear the tab knows, and the service refuses them, changing nothing, when it holds another; the reply names that clear and its time, and the tab sends again counting only its runs from then on, turning their times onto the service's clock with the offset from the reply's `now`. So a stale device can't bring cleared numbers back, and runs made after a clear that went out late still count. An undo of a clear that is no longer the latest is refused: the newer clear wins. The undone tab keeps its restored history and says, where the undo was made, that the board keeps the newer clear. An undo also names the clear before it that it counts its runs from, and the service refuses it, changing nothing, when that isn't the clear it would put back (another device cleared after this tab last heard from the board, then this tab cleared); every reply names the clear before the latest, so the tab counts from that one, and a refused undo goes again from it. So an undo never puts back a clear together with the runs that clear removed. A clear or undo the service hasn't confirmed (offline, or a failed request) is kept on the device, one record per clear (`stilltype-board-replace:<account id>:<clear id>` in localStorage), and sent before any other write on the next load or board read, until the service confirms it. Only the tab that made a clear writes its record, but any tab may send any record, since the service answers a repeat as done: kept clears and undos go in the order they were made, the tab's own among them, before its other writes (a tab that sees another tab's record and still finds it kept five seconds later sends it too, never mid-run); the tab that gets the service's answer removes the record. Another tab's record never takes the place of a tab's own clear or its Undo. An undo of a clear not yet confirmed, including one made while the clear's request was still on its way and then failed, sends the clear and then the undo. The extra round trip happens only after a clear the tab missed since it last heard from the board (a tab's first write after loading is preceded by one quiet read, which names the latest clear). A tab sends one write at a time, in order: a change made while a write is in flight waits for it and then sends the latest summary, so an earlier publish never lands after that tab's clear or undo. Each daily result carries its version (the daily conditions key, which includes the corpus and metric version, and the passage); a reader on another build sees it as "another version of the daily · not compared" rather than ranked. The service accepts only plausible values (0–400 wpm, 0–100% accuracy, a daily date within a day of the server's UTC date, a printable version of at most 200 characters, a Monday week start within a week of the current one, at most a week of seconds) and shows a daily result only for today's UTC date and practice time only for this UTC week. The numbers are reported by browsers and are not verified; they never enter progress or bests.
- **Storage.** `race_private.summaries` holds one row per account that has shared (RLS on, no browser privileges): `sharing`, the latest clear (`clear_id`, `clear_from`), the one before it (`undo_id`, `undo_from`), the clear the last undo took back (`undone_id`) and the last twenty clears applied (`seen_clears`), and the daily and week numbers (null in the opt-out marker). `bests` holds the bests as a JSON object keyed by condition key, each `{ wpm, accuracy, date }`; a check constraint (`race_private.valid_bests`) holds every row to the limits above (a date by its format only) and keeps the marker's empty. The reply tells a reader only their own sharing state, latest clear and the clear before it. `public.friends_board` is an invoker wrapper, granted to signed-in accounts only, around the definer `race_private.board`, which only ever writes the caller's own row and builds the reply with `race_private.board_snapshot`.

The migration is `supabase/migrations/20261009120000_friends_board.sql`; `supabase/tests/friends-board.sql` covers privileges, guests, opt-in sharing (nothing stored before it, the opt-out marker, refused writes after it, sharing again), value and version limits, merging a stale tab's summary, replacing after a clear or undo, refusing a publish or share that missed a clear, keeping a late clear's own time, turning a clear from a clock an hour behind into the service's time and clamping one from the future, taking clears in arrival order without moving their time back, answering a repeated clear or undo as done (folding its runs in while it is still the latest, and changing nothing once a newer clear or its undo has overtaken it), refusing an undo after a newer clear or one that counted from another clear than the one it would put back, account deletion, one-way and mutual lists, unconfirmed emails, duplicate list entries, stale days and weeks under a non-UTC session time zone, clearing and removal. All three SQL test files pass against the five migrations on PostgreSQL 16 with the minimal `auth` / `extensions` stub. The board test makes every call the way PostgREST does, as the `authenticated` role with the user's id in the JWT claim (as `anon` for a guest), so a missing grant on the call path fails it. **Apply the migration before shipping the frontend**: until then the board reports that it is being set up, and publishing after runs fails quietly.

Bests are added by `supabase/migrations/20261009150000_friends_bests.sql`, which must be applied after `20261009120000_friends_board.sql`, before or with the frontend that sends them. It adds the `bests` column and its check, and helpers that only the board calls (`race_private.sent_bests`, `fold_bests`, `bests_since`), and replaces `race_private.board_snapshot` and `race_private.board` with copies that add lines for bests and change nothing else: every added line mentions bests, and `tests/friends-bests.test.js` checks that taking those lines out gives back the earlier functions exactly, so a later change to them must be carried over. `supabase/tests/friends-bests.sql` covers privileges, guests, opt-in, mutual friends only (not one-way lists, non-sharers, or anyone while the reader doesn't share), rows carrying no ids, every limit, folding (slower, equal-but-later and better bests), the 16-shape cap, a clear replacing them, a device that missed the clear (refused however it writes), an overtaken or earlier clear changing nothing, a repeated clear folding in, the undo putting them back (and repeated), an undo after a newer clear refused, the clear-boundary cut for publishes, clears and undos, the opt-out marker, the table's own check, and account deletion. ## Storage and access

- `src/multiplayer.js` calls `public.race_action` using the existing browser publishable key and a member token when signed in. It refreshes sessions and maintains progress sequence numbers across reloads.
- `race_private.rooms` and `race_private.players` enable RLS and grant browsers no table privileges. An explicitly granted invoker RPC calls a private definer function that checks account membership or an independent guest-seat capability on every operation. Transitions lock the room row; hosting quotas serialize by account. A rematch counts against the racer who asks for it (their account, or a guest's seat), not the original host.
- Account lookups stay inside the database. Snapshots omit account IDs, emails, capability hashes and the other player’s typed text/counters. Both players can see names, readiness, progress and scores.
- A guest invitation and the joined guest’s seat use different random 256-bit capabilities. Only hashes are stored in the database. Invitation capabilities live in URL fragments; joined-seat credentials and the host’s link are retained only in the current tab’s sessionStorage, along with any pending invite needed through sign-in redirects. Solo guest history is still not persisted.
- Room data includes current typed text, counters and scores. Creating a room opportunistically removes rooms whose expiration was more than a day ago; there is no scheduled deletion guarantee while the app is idle.

The migration is `supabase/migrations/20260930085227_online_races.sql`, applied to project `bicbyljexprkaedakofa` (`typingsite`) as remote migration `20260930085736`. No new runtime dependency or WebSocket server is required. The static frontend build uses the existing hosting workflow; this change does not publish a frontend deployment.

## Verification

The build and all four Node test files pass. The 48 Chromium scenarios pass across the full regression run and the final targeted rerun of the updated reduced-motion assertion. Desktop dark and 320 px light lobby screenshots were visually reviewed.

`npm test` covers existing scoring/accounts plus transport payloads, fragment parsing, capabilities and reconnect sequencing. `e2e/multiplayer.spec.js` drives independent browser contexts against shared in-memory Supabase state: full race/results, account inbox, host/guest reload, mid-race progress restoration, cancellation, occupied links, expiration, offline recovery and 320 px layouts in both themes. The fake is for browser orchestration, not proof of database security.

`supabase/tests/online-races.sql` was separately executed against the deployed database. It creates temporary test users inside a transaction and rolls everything back. Assertions cover host authorization, unauthorized readers, guest capability isolation, pre-start rejection, impossible counters, incomplete early finishes, server scoring, stale updates, account invite isolation and cancellation. Catalog checks confirmed both private tables have RLS and no browser read/write privileges.

The Supabase security advisor reports informational [RLS without policies](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) for these intentionally inaccessible private tables. An existing project-level [leaked-password protection setting](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) is unchanged.

Browser verification uses Chromium. Real cross-region latency, physical mobile keyboards and full anti-cheat remain unmeasured. Public matchmaking, ratings and email delivery are outside this feature.
